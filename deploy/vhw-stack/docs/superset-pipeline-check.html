Health check (about five minutes)

Every command below only reads. Run them on analytics-host.

  1. Are the containers up, and have they restarted?

    sudo docker ps -a --format '{{.Names}}' | grep -iE "pipeline|spark|superset" | while read c; do
  sudo docker inspect "$c" --format "{{.Name}}  status={{.State.Status}}  restarts={{.RestartCount}}  OOMKilled={{.State.OOMKilled}}  started={{.State.StartedAt}}"
done
    Healthy: every container running except superset_init (exited, exit 0); restarts=0; OOMKilled=false.

  2. Did the hourly run happen?

    sudo docker logs --since 2h pipeline-controller 2>&1 | grep "Last run was at" | tail -1
curl -s -m 10 http://127.0.0.1:8090/status; echo
    Healthy: "Last run was at" shows today, within the last hour or so; status is IDLE between runs or RUNNING just after the hour.

  3. Is the data fresh?

    In Superset: SQL → SQL Lab. In the Database dropdown (top left) choose BKM_Server, schema default, then run:

    SELECT count(*) AS tasks, max(meta.lastUpdated) AS newest FROM task;
SELECT count(*) AS patients FROM patient;
    Healthy: newest is the same as the newest change on production (next step). On quiet days nobody syncs, so an older newest is fine as long as production has nothing newer.

    "PostgreSQL Error: relation "task" does not exist" means another database is selected in the dropdown. The pipeline's tables are only in BKM_Server.

  4. Does production have anything newer, and can the pipeline reach it?

    curl -s -o /dev/null -m 10 -w 'production FHIR: %{http_code}\n' http://prod-host:8080/fhir/metadata
curl -s "http://prod-host:8080/fhir/Task?_sort=-_lastUpdated&_count=1&_elements=id" | grep -o '"lastUpdated": *"[^"]*"' | tail -1
curl -s -o /dev/null -w 'paging links from this server: %{http_code}\n' "https://vhw.gov.ls/fhir/Task?_count=1&_summary=count"
    Healthy: 200; the newest task on production has the same time as newest in step 3, or is less than an hour newer (the next run brings it in); the paging check gives 200, not 401.

  5. Memory and disk

    free -h; df -h /
    Healthy: a few GB "available" memory; disk well below 90%. On 13 Oct: 16 GB available, disk 27%.

Do not change the pipeline settings or delete its data folders without the technical team. A full reload from production is safe and takes a few minutes at today's data size (13 Oct: about 7,400 tasks); Superset keeps showing the previous data until it finishes. The pipeline page (port 8090) only opens inside the network; the curl commands above do the same from the server.

What we did

6 Oct 2026

The pipeline had stopped in January and was set to read an old database that no longer existed, so the dashboards showed months-old data.

  • Switched the pipeline to read production FHIR directly (prod-host:8080), incrementally every hour.
  • First full load: 1,477 patients and 7,363 tasks.
  • All containers set to start again by themselves after a reboot or power cut.
  • Prepared the BKM Child Health dashboard (vaccines, routine visits, children) as an import file.
13 Oct 2026

Reported as "Data pipeline and Spark crashing". Checked:

  • All containers running, no restarts, none killed for memory.
  • Hourly runs on schedule (last run 06:00 UTC, next 07:00 UTC).
  • The errors in the logs are the normal messages listed above, caused by Superset looking up the BKM dataset names.

Nothing was crashing, but no new data had arrived since 6 October. Cause: each hourly run found the changes on production, then followed production's paging links to https://vhw.gov.ls/fhir, where the gateway refused it (HTTP 401) because the pipeline has no login. The run still reported "finished", with nothing imported.

  • Fix (13 Oct, 09:20): on the proxy proxy-host, /fhir requests from the Superset server only (analytics-host) now go straight to production FHIR on port 8080; everyone else still goes through the gateway and needs a login. This gives the Superset server no access it did not already have.
  • One full load run the same morning (curl -X POST "http://127.0.0.1:8090/run?runMode=FULL" on analytics-host). Verified in SQL Lab: 7,363 tasks, newest change 12 Oct 14:42, so the missing changes are in.
  • Server time zones set to Lesotho time (SAST) on production, test, Superset and the proxy; all clocks synchronised (tools/check_server_time.sh from the jump host shows them side by side).
  • Original proxy file kept as /root/vhw.gov.ls.bak-20261013-0918 on proxy-host.
  • Planned proper fix: a read-only service login for the pipeline through the gateway, after which this proxy rule and the open port 8080 can be removed.
