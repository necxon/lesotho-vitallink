Reading the diagrams
  • Dashed outlines are trust boundaries, not subnets — everything below the edge runs on one host.
  • A port on a node is what that service listens on; a port on a link is what the caller dials.
  • Ports written as host :8081 are the host publication of a container port.
Deployment variants
  • Domain server: only 22, 80 and 443 open; Figure 1's service ports stay on loopback.
  • IP-only server with no domain: those eleven service ports are opened directly with ufw allow and served over plain HTTP.
  • Sandbox on a laptop: same bindings, no firewall in front.
  • Mixed hosting: any component system can be repointed at another IP without touching the rest of the stack.
Pointing a system elsewhere
  • Set the system's base URL on the middleware — OPENLMIS_AUTH_URL, OPENLMIS_MGMT_URL, OPENLMIS_REF_URL, DHIS2_URL, OPENSRP_URL or HAPI_FHIR_URL.
  • The repo default points all six at the in-stack instances; using a partner system is a per-deployment override, not a code change.
  • The in-stack containers can then be left out of the compose file, freeing their host ports.
  • Credentials follow the endpoint — a partner system needs its own client and token settings.
Source of truth
  • docker-compose.yml — bindings and container ports

  • deploy/setup-server.sh — firewall allow-list
